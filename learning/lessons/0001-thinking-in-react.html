Thinking in React

Decompor a Home em componentes e classificar cada dado como estático, estado ou derivado. O objetivo é ter o mínimo possível de estado.

Pré-requisito: nenhumAplica em: ../src (Home)Referência: folha de consulta

1. A diferença que muda tudo

Um componente Angular é uma instância de classe que vive enquanto está na tela. Os campos dela são memória, e você é responsável por mantê-los atualizados (ngOnChanges, subscribe, setters).

Um componente React é uma função que roda de novo a cada render. Não existe this. As variáveis locais nascem e morrem em cada execução. O que precisa durar entre renders tem que ser declarado explicitamente como state (useState); todo o resto é recalculado.[pure]

Consequência: derivar um valor no render é de graça e nunca fica dessincronizado. Guardar em state um valor que dá para calcular cria uma segunda fonte de verdade, e aí você precisa sincronizar as duas.

2. As três perguntas

O react.dev manda encontrar a representação mínima, mas completa do estado, seguindo DRY: “compute everything else on-demand”.[TiR §3] Para cada dado:

  1. Não muda com o tempo? Então é estático. Na viagem: módulo TS importado (trip.ts), não state.
  2. Vem do pai via props? Então não é state deste componente.
  3. Dá para calcular a partir de props/state existentes? Então é derivado, e “definitely isn't state”.

Sobrou? É estado. Na prática a Home inteira tem pouquíssimo estado.

Você vai querer escrever isto (é o ngOnChanges com outra roupa):

const [totalDias, setTotalDias] = useState(0);
useEffect(() => {
  setTotalDias(diffInDays(trip.start, trip.end));
}, [trip]);

O primeiro render mostra 0, depois vem um segundo render, e você tem duas fontes de verdade. O react.dev chama isso de “redundant state and unnecessary Effect”.[YMNNAE]

const totalDias = diffInDays(trip.start, trip.end);

Se você já usou signals: o corpo inteiro do componente funciona como um grande computed(). useMemo só entra quando o cálculo é caro de verdade, não “por garantia”.[useMemo]

3. Onde o estado mora

Para cada estado:[TiR §4] (1) liste todos os componentes que renderizam algo com base nele; (2) ache o ancestral comum mais próximo; (3) coloque o estado ali ou acima. Se nenhum fizer sentido, crie um componente só para guardá-lo.

Para mudar o estado lá de baixo, o dono passa o setter como callback prop: é o inverse data flow.[TiR §5] Não existe [(ngModel)]. O equivalente explícito é value + onChange.

O reflexo é criar um TripStateService providedIn: 'root' e jogar tudo lá. Em React, o default é deixar o estado no ancestral comum mais próximo. Context é um mecanismo de transporte para evitar prop drilling; ele não substitui “decidir quem é o dono”. Isso fica para uma lição futura.

Exercício C · Code review

1. O tema afeta o ícone do ThemeToggle e o estilo da página inteira. Onde o state do tema mora?

  1. No ThemeToggle, que é dono do botão
  2. No App, o ancestral comum mais próximo
  3. Num módulo singleton, no estilo de service
  4. No localStorage, lido diretamente em cada render

2. Num PR aparece: const [dias, setDias] = useState(0); useEffect(() => setDias(diff(trip.start, trip.end)), [trip]);. Qual é o comentário certo?

  1. Faltam trip.start e trip.end no array deps
  2. Trocar o useEffect por useMemo resolve tudo
  3. Estado redundante: calcule direto durante o render
  4. O useEffect roda antes do primeiro render

3. Na página de Hospedagens, clicar num pin do mapa destaca a hospedagem na lista. O que entra no state?

  1. O objeto inteiro da hospedagem que foi selecionada
  2. Um campo booleano isSelected dentro de cada hospedagem
  3. Uma cópia da lista marcando qual está selecionada
  4. Somente o id da hospedagem que foi selecionada

4. “Próximos passos” depende da data de hoje. Qual é o melhor desenho?

  1. Receber now como parâmetro e filtrar no render
  2. Guardar a lista filtrada dentro de um useState
  3. Recalcular a lista num useEffect de dependências vazias
  4. Chamar new Date() dentro de cada item renderizado
